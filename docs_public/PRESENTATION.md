# 🎤 MovieFactory — Project Presentation

본 문서는 MovieFactory 프로젝트를  
**발표·면접 상황에서 설명하기 위한 문서**이다.

기능 나열이 아니라  
**문제 인식 → 설계 판단 → 기술적 근거 → 확장 방향**의 흐름으로 구성된다.

---

## 1. 문제 인식

많은 ML / 추천 시스템 프로젝트는 다음과 같은 한계를 가진다.

- 노트북 기반 실험에서 끝난다  
- 모델 성능만 강조되고 구조가 없다  
- 실행 환경이 바뀌면 재현이 어렵다  
- 실제 서비스 형태로 연결되지 않는다  

즉,  
**“추천 모델을 만들었다”와  
“추천 시스템을 설계했다” 사이에는 큰 간극이 존재한다.**

---

## 2. MovieFactory의 목표

MovieFactory는 이 간극을 해결하기 위해 시작되었다.

목표는 단 하나다.

**“ML / DL 기반 추천 시스템을  
처음부터 끝까지 실행 가능한 서비스 구조로 구현할 수 있는가?”**

이를 위해 성능 경쟁이 아닌  
**구조적 완결성과 재현성**을 우선했다.

---

## 3. 핵심 설계 판단

### 3.1 단일 Builder 중심 구조

- 모든 실행은 Builder에서 시작한다  
- 동일한 디렉토리 구조와 동일한 결과를 보장한다  
- 수동 설정을 제거한다  

그 결과,  
**누가 실행해도 같은 프로젝트가 생성된다.**

---

### 3.2 project_root 기준 통합 설계

- 데이터  
- 캐시  
- API  
- UI  
- Dashboard  

모든 컴포넌트가  
**하나의 기준 경로(project_root)** 를 공유한다.

이를 통해  
환경 차이로 인한 실행 실패를 제거했다.

---

### 3.3 엔진 책임 분리

MovieFactory는 4개의 독립 엔진으로 구성된다.

- SBERT: 의미 기반 텍스트 유사도  
- TF-IDF: 키워드 기반 보정  
- Synthetic CF: 행동 지표 기반 유사도  
- Hybrid: 엔진 결과 결합  

각 엔진은  
- 서로를 직접 호출하지 않고  
- 캐시를 통해서만 연결된다  

이로 인해  
**결합도는 낮추고, 교체 가능성은 높아진다.**

---

## 4. 왜 이 프로젝트가 의미 있는가

MovieFactory는 다음을 증명한다.

- ML 모델을 “썼다”가 아니라  
- ML 시스템을 “설계했다”  

라는 점이다.

특히 다음 요소들이 차별점이다.

- 엔드투엔드 실행 가능  
- 서비스 구조를 전제로 한 설계  
- 재현 가능한 결과  
- UI / API / Analytics 분리  

---

## 5. v1에서 의도적으로 제외한 것

다음 요소들은  
**기술적으로 가능하지만 v1에서는 의도적으로 제외**했다.

- LLM / RAG  
- Online Learning  
- 사용자 로그 기반 개인화  

이유는 단순하다.

**구조가 안정되지 않은 상태에서  
기능을 늘리는 것은 오히려 완성도를 떨어뜨리기 때문이다.**

---

## 6. 확장 방향 (v2+)

MovieFactory는 v2 이후 다음 방향으로 확장 가능하다.

- 사용자 행동 로그 기반 CF  
- LLM 기반 추천 설명 레이어  
- A/B Test 기반 랭킹 비교  
- Online Feature Store 연계  
- 실시간 추천 파이프라인  

v1은 **끝이 아니라 기반**이다.

---

## 7. 한 문장 요약

MovieFactory는  

**“추천 모델을 만드는 프로젝트가 아니라,  
추천 시스템을 설계하고 재현하는 프로젝트”**다.

이 점이 이 프로젝트의 가장 큰 가치다.
